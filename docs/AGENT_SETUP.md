# Vibe — использование команды Codex

Конфигурация инфраструктуры, 10.10.2026. Требования/архитектура в остальных документах имеют статус DRAFT. Фактические проверки записаны отдельно в SETUP_VALIDATION.md.

Инструкция владельцу с готовыми поручениями для каждой роли — [AGENT_USAGE.md](AGENT_USAGE.md).

## Формат и локальная версия

При первичной настройке обнаружен Codex CLI `0.162.0-alpha.2`, `codex features list` показывал `multi_agent stable true`. После перезагрузки 10.10.2026 локальный CLI — `0.162.0-alpha.17.2`; загрузка пяти ролей и native reviewer проверены повторно. В текущем чате доступен официальный инструмент запуска субагентов; лимит среды — четыре активных агента, включая координатора.

Проектная `.codex/config.toml` содержит `[agents]` с enabled=true и максимумом трёх дочерних потоков. Пять именованных деклараций с description/config_file указывают на отдельные `.codex/agents/<role>.toml`. Каждый файл задаёт name, description и developer_instructions. Модель и reasoning намеренно не заданы: наследуются от основного сеанса и не предполагают доступность конкретной модели.

Reviewer дополнительно задаёт sandbox_mode="read-only" и approval_policy="never". Это настройки, а не доказательство их фактического применения. Живые overrides основного сеанса могут переопределить sandbox custom agent; tools текущего чата могут не иметь выбора роли. Поэтому координатор обязан проверить выбранную политику перед заявлением о технической защите.

Официальные источники, проверены 10.10.2026: [Subagents и custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Project config и доверие](https://learn.chatgpt.com/docs/config-file/config-basic), [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md). Конкретный перечень поддержки установленной версии подтверждается диагностикой, а не только документацией.

С явного разрешения владельца («Разрешаю доверие только StablePlan» — историческое имя до переименования в Vibe) добавлена единственная запись доверия `projects.'c:\myapps\myprojects\vibe'.trust_level="trusted"` в пользовательский `C:\Users\vhnkg\.codex\config.toml`. Перед записью создана резервная копия; проверено, что остальные данные конфигурации не изменились. Модель и прочие глобальные настройки не менялись. Флаг включения experimental multi_agent не требуется, если effective agents.enabled и feature уже включены. Для других недоверенных проектов координатор не меняет trust_level самостоятельно. Папка проекта и запись доверия уже используют Vibe, поэтому переименование документов не требует новой глобальной записи.

## Активация и проверки

1. Открыть основной Codex-сеанс в `C:\MyApps\MyProjects\Vibe`; новый сеанс перечитает AGENTS.md и проектные роли. Уже работающий сеанс может требовать нового запуска/перечитывания; не предполагать горячую загрузку.
2. Проверить effective project config и доступность пяти ролей. Если проект не доверен, владелец подтверждает доверие через штатный UI/CLI. Не обходить ограничение session override без решения владельца.
3. В PowerShell из папки проекта запустить `python scripts/check_agents.py` (Python ≥ 3.11): TOML и структура без записи.
4. Запустить `python scripts/probe_codex.py`: app-server config/read со strict-config и debug prompt-input, без обращения к модели. Вывод ограничен настройками agents и метаданными слоёв.
5. Поручить безопасную проверку custom agents: architect анализирует документацию, reviewer читает AGENTS.md; никаких прикладных правок. Убедиться в фактическом выборе ролей и политике. `/agent` в интерактивном CLI позволяет осмотреть потоки; это не команда вызова конкретной роли.

В первичной проверке до переименования все пять деклараций действительно загружены, native custom architect/reviewer запущены; чтение и legacy canary блокировались ошибкой Windows sandbox. После перезагрузки обычное чтение работает, пять деклараций загружаются, native custom reviewer в отдельном read-only/never запуске прочитал файлы и получил отказ единственной контрольной записи. Маркер не создан; новый setup refresh проходит без ошибок. Эти новые проверки выполнены без MXC override. Подробные исторические и актуальные статусы — SETUP_VALIDATION.md.

`--strict-config` поддерживается не каждым подкомандным диагностическим режимом этой версии: проверка через `features`/`debug` с этим флагом отклоняется. Для парсера используется app-server. Наличие имени роли в тексте AGENTS.md не доказывает применение её TOML при spawn.

Не использовать `--yolo`/danger-full-access для reviewer. Если Windows sandbox не запускает процессы, техническую проверку записи помечать UNVERIFIED; правило отсутствия записи сохраняется. Нельзя объявлять отказ запуска shell доказательством запрета записи.

Если инструмент текущего чата не выбирает custom type или живые overrides расширяют права reviewer, официальный отдельный read-only запуск может выглядеть так:

```powershell
codex --ask-for-approval never exec --skip-git-repo-check --strict-config --sandbox read-only "Запусти custom agent reviewer без наследования истории; проверь AGENTS.md без изменений файлов, дождись ответа и сообщи фактический sandbox"
```

`--ask-for-approval` здесь относится к главной команде и стоит перед `exec`. `--skip-git-repo-check` нужен в текущей папке без Git. Это запуск диагностики/ревью, основной координатор остаётся в исходном чате. В проверенном `--ephemeral` smoke-test наследование истории вызвало `no rollout found`; повтор с `fork_turns=none` сработал. Поэтому не рассчитывать на fork истории временного сеанса этой версии. Отдельный запуск не исправляет ошибку Windows sandbox и не даёт разрешения на обход.

## Восстановление Windows sandbox: предложение

Предложение ниже относится к первоначальному сбою. После перезагрузки ноутбука чтение и запрет записи reviewer прошли проверку; постоянное переключение на MXC для устранения этого блокера сейчас не требуется. Фактическую политику роли всё равно проверять перед каждым новым способом запуска.

Диагностика 10.10.2026 обнаружила `os error 32`: legacy setup не может обновить ACL занятого `node_repl.exe`. Первый способ — сохранить работу, полностью закрыть Codex и связанные CLI-сеансы, затем открыть приложение снова. Если runtime-процессы остались, перезагрузка Windows освобождает их без ручного изменения ACL. После запуска повторить обычное чтение и тест read-only. Это предложение; приложение и процессы автоматически не останавливались.

Альтернатива при повторении сбоя — MXC. На этом компьютере официальный compatibility probe завершился MXC_OK, а отдельный MXC read-only запуск разрешил чтение и отклонил запись. Для разового CLI-запуска можно добавить `-c windows.sandbox=mxc`; это не сохраняет настройку. Для постоянного выбора предлагается значение `sandbox = "mxc"` в существующей секции `[windows]` пользовательского config.toml. Другие значения сохраняются; глобальный файл координатор меняет только по отдельному согласию владельца. Доверие к Vibe такого согласия на смену sandbox не даёт.

MXC — рекомендованный механизм на совместимых Windows; проверочная команда и способы восстановления legacy описаны в [официальной документации Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox), проверенной 10.10.2026. После выбора механизма открыть новый сеанс Vibe и проверить реальный custom reviewer: роль загружена, чтение работает, фактическая политика read-only/never, контрольная запись отклоняется и файл не создаётся. Успех отдельного sandbox probe не заменяет эту проверку роли. Если сбой останется, проверить доступное обновление Codex штатным интерфейсом и приложить журнал ошибки для диагностики.

## Запросы обычным языком

Эти запросы — поручения координатору, который сам выбирает нужные роли; это не выдуманные slash-команды:

- «Поручи architect уточнить модель повторений и недельных целей. Верни варианты и вопросы для моего утверждения, без кода».
- «Поручи reviewer проверить AGENTS.md и конфигурацию команды без изменений файлов».
- После разрешения реализации: «Реализуй создание задач в Vibe. Организуй работу нужных агентов, проверь результат и покажи мне изменения».
- «Пусть backend исправит подтверждённую ошибку синхронизации, android проверит клиентский сценарий, а reviewer оценит изменения. Не коммить».
- «Поручи frontend добавить согласованный экран статистики, затем проверь его с reviewer».

Координатор сначала читает решения и проверяет разрешённый этап. Если новый запрос затрагивает неутверждённый общий контракт, готовит конкретное предложение и запрашивает согласие на него; мелкие изменения согласованной задачи выполняет самостоятельно.

## Поручение агенту и сборка результатов

Пример: цель — проверить создание офлайн-задачи; роль — android; вход — утверждённый DTO и sync-протокол; файлы — назначенный Android worktree; запрет — не менять сервер/контракт; зависимость — backend поддерживает opId; приёмка — Room-данные и outbox переживают process death; проверка — релевантные unit/integration/device tests; итог — файлы, фактические команды/результаты, риски.

При отсутствии worktree писать последовательно. Отдельные ветки в общей папке не защищают файлы от параллельного редактирования. 13.10.2026 Git инициализирован и D1 опубликован по GH-01. Для C1 созданы отдельные managed worktree Backend и Web, однако запись вне основной папки недоступна текущему Windows sandbox. Поэтому код C1 записывается последовательно в разрешённом workspace с одним автором одновременно, без коммитов/merge. Новые commit/push требуют отдельного разрешения.

Координатор проверяет решения и пересечения ответственности, организует проверки и reviewer, направляет замечания автору, затем показывает владельцу итог. Reviewer не исправляет файлы. Результат smoke-test относится только к проверенным инструментам/режиму, не доказывает автоматически работу каждого будущего сеанса или права клиента.
