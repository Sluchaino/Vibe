# Vibe — как пользоваться ролями

Инструкция владельцу проекта, 10.10.2026. Архитектура в целом DRAFT; владелец разрешил разработку и отдельно утвердил T0 — технический каркас Backend/Web. Роли могут реализовывать явно выбранный срез; предметный D1 и общий API пока требуют выбора. Android не отменён, подготовка его среды отложена.

## Быстрый старт

1. Открой чат проекта Vibe, работающий в `C:\MyApps\MyProjects\Vibe`.
2. Напиши цель и, если знаешь, нужную роль: «Поручи architect…» или «Поручи reviewer…».
3. Укажи результат: предложение, список проблем, правки разрешённых файлов или проверенные изменения.
4. Координатор запустит подходящих агентов, дождётся ответов и вернёт общий результат. Архитектурные решения выбираешь ты.

Готовый запрос для следующего архитектурного шага:

> Поручи architect разобрать ADR-01 и ADR-02 из docs/DECISIONS.md. Объясни варианты простыми словами, причины выбора и риски. Затем поручи reviewer проверить предложение. Дождись обоих результатов и верни мне список решений для утверждения. Файлы не менять, код не создавать.

Указанные ниже сообщения — примеры для копирования. Их наличие в инструкции само по себе не запускает работу.

## Как выбрать роль

| Роль | Когда поручать задачу | Что получить |
| --- | --- | --- |
| Координатор — основной чат | Функция затрагивает несколько компонентов или непонятно, кого выбрать | Разделение работы, порядок зависимостей, общий результат и вопросы владельцу |
| `architect` | Модель данных, границы модулей, общий API, синхронизация, планирование | Предложение с альтернативами, рисками и решениями для утверждения |
| `backend` | Сервер: C#, ASP.NET Core, PostgreSQL, EF Core | Серверный дизайн; после разрешения — реализация и серверные проверки |
| `android` | Android: Kotlin, Compose, Room, офлайн-работа и таймер | Клиентский дизайн; после разрешения — приложение и Android-проверки |
| `frontend` | Web: React, TypeScript, календарь, задачи, статистика | Предложение интерфейса; после разрешения — веб-интерфейс и проверки |
| `reviewer` | Независимая проверка предложения или завершённых изменений | Замечания с приоритетами и доказательствами; исправления делает автор |

## Поручения на текущем этапе

**architect**

> Поручи architect проверить модель повторений и недельных целей. Вход: docs/DATA_MODEL.md и docs/DECISIONS.md. Верни варианты, спорные случаи и вопросы для моего выбора. Без правок файлов и кода.

**backend**

> Поручи backend оценить серверную защиту от повторной отправки одной операции. Вход: docs/SYNC_DESIGN.md. Нужны сценарии двух устройств, риски и план тестов. Общий API не утверждать, код и файлы не менять.

**android**

> Поручи android описать сценарии офлайн-таймера: пауза, закрытие приложения, перезагрузка телефона, восстановление сети. Выдели вопросы для architect и предложи проверки. Без кода и изменений файлов.

**frontend**

> Поручи frontend предложить поведение календаря при просмотре перепланирования и отказе подтверждения устаревшего плана. Верни состояния экрана, ошибки и вопросы по API. Без кода и изменений файлов.

**reviewer**

> Поручи reviewer проверить docs/DATA_MODEL.md и docs/SYNC_DESIGN.md на противоречия. Работать без записи; координатор проверяет фактическую политику read-only/never. Верни замечания с приоритетом, местом и объяснением. Черновые предложения не считать утверждённой архитектурой.

## Когда разрешишь реализацию

Сначала выбери конкретные решения и их параметры. Например:

> Утверждаю ADR-01 в следующей формулировке: [выбранное решение и параметры]. Зафиксируй это в docs/DECISIONS.md. Остальные ADR остаются предложениями. Реализацию пока не начинать.

Затем отдельно поручай ограниченный участок реализации. Следующий шаблон применяется после утверждения нужной архитектуры, структуры каталогов и API:

> Разрешаю реализацию [функция] по [утверждённые решения и контракт]. Поручи [backend / android / frontend] выполнить её в [назначенные файлы]. Критерии готовности: [проверяемые результаты]. Общий API самостоятельно не менять. Запусти подходящие проверки, затем передай результат reviewer. Замечания исправляет автор. Верни изменения, результаты проверок и оставшиеся риски. Без коммитов и push.

Для функции из нескольких компонентов можно поручить координацию:

> Организуй реализацию [согласованная функция]: backend готовит серверную часть, android и frontend подключаются к утверждённому API, reviewer проверяет итог. Сначала сообщи зависимости и владельцев файлов. Без Git worktree изменения выполнять последовательно. Дождись проверки и покажи общий результат.

В проекте настроен максимум три дочерних агента одновременно. Пять ролей используются по необходимости и по этапам. Сейчас Git/worktree отсутствует, поэтому запись выполняется последовательно. Разрешения на коммит, push и публикацию даются отдельно.

## Как уточнять задачу и смотреть результат

Пиши в основной чат:

- «Покажи работающих агентов: роль, задача, статус и что ещё осталось».
- «Передай architect уточнение: [новое ограничение]. Остальное поручение сохранить».
- «Останови android и сообщи, что он успел выполнить и какие файлы изменены».
- «По результату reviewer поручи автору исправить P1 и P2, затем повторить затронутые проверки».
- «Объясни замечание reviewer простыми словами и предложи варианты решения».

В итоговом отчёте проси перечислять фактически использованные роли, изменённые файлы, выполненные проверки, незапущенные проверки и решения для тебя. Отсутствие замечаний reviewer не заменяет тесты.

## Если используешь CLI

Открой PowerShell и запусти основной сеанс в проекте:

```powershell
Set-Location -LiteralPath 'C:\MyApps\MyProjects\Vibe'
codex
```

Поручения ролям вводятся обычным текстом. `/agent` в интерактивном CLI переключает уже существующие потоки; конкретную роль запрашивай в поручении координатору. В приложении можно открыть доступные карточки активности субагентов и посмотреть результаты. Эти возможности описаны в [официальной документации Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Настройки reviewer из TOML могут быть переопределены живой политикой родителя. Проверка фактических прав — задача координатора; при необходимости он использует отдельный read-only CLI-запуск. Техническая инструкция находится в [AGENT_SETUP.md](AGENT_SETUP.md), подтверждённые проверки — в [SETUP_VALIDATION.md](SETUP_VALIDATION.md).

Для небольшого вопроса достаточно основного чата. Делегирование полезно, когда нужен отдельный специалист или независимая проверка; запуск всей команды для каждого вопроса не требуется.
