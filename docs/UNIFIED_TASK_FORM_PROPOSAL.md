# U1 — единая форма задачи

Статус: ACCEPTED / 19.10.2026. Владелец выбрал «Утвердить U1 и реализовать» в ответ на этот пакет, включая Backend/Web и новые правила хранения/API для отсутствующих даты/объёма, interval-повторения и одинаковых часов серии с безопасным размещением. Решение U1 записано в DECISIONS.md. Разрешены точный контракт и реализация; повторное согласование того же пакета не требуется. Источник интерфейсного направления — WEB-UX-04.

## Форма

Без вкладок «Одноразовая» / «Повторяющаяся». Порядок:

1. Название — обязательно.
2. Описание — необязательно.
3. Дата выполнения и начало — необязательно, выбираются раздельно.
4. Конец выполнения — необязательно; вместе с началом образует интервал в выбранную дату.
5. Дата окончания повторения — необязательно, включительно.
6. Дни повторения и список режимов: не повторять, каждый день, будни, выходные, выбранные дни, каждые N дней. Дополнительные «не повторять» и «выбранные дни» предложены для явного сохранения задачи без повторения и произвольного набора дней.
7. Полный объём, минуты — необязательно.
8. Фиксация после размещения.
9. Категория, важность, сложность, приоритет — отдельные характеристики.

Выбор дней включает weekly-повторение; каждый день/будни/выходные заполняют соответствующий набор. «Каждые N дней» — отдельный режим с числовым N, без скрытого пересечения с фильтром дней недели. По умолчанию предлагается «Не повторять».

## Уточнения владельца

- 19.10 владелец пояснил: выбираются дата и время, например с09:00 до11:00; в ответе конец назван «концом повторения». Координатор уточнил смысл:11:00 — конец конкретного выполнения в выбранный день, «Дата окончания повторения» отдельно ограничивает серию. Дедлайн не предлагается.

## Конкретный пакет U1 для выбора

Владелец утвердил перечисленные ниже правила вместе с соответствующими API/хранением и реализацией Backend/Web отдельным ответом «Утвердить U1 и реализовать»; одни лишь прежние пояснения не использовались как согласие.

- Полный интервал, например09:00–11:00, явно показывает вычисленный объём120 минут. Это плановый объём, не факт работы. При смене времени автоматически вычисляемый объём пересчитывается; отдельно введённый вручную объём не теряется.
- Начало и ручной объём вычисляют конец; конец и ручной объём вычисляют начало. Если введены все три, значения должны согласовываться: ошибка вместо скрытого сокращения/увеличения объёма. Вычисленная соседняя дата показывается явно. Меньшее время конца без явного следующего дня не означает автоматически ночь.
- Только начало или только конец без объёма сохраняется как неполное намерение, без календарного блока. Для часов нужна дата. При отсутствии часов и объёма задача сохраняется без времени. Дата без часов допускается и используется в календаре как карточка, не занимающая время.
- Если дата также не задана, создаётся действительно недатированное выполнение. Оно отображается отдельной группой «Без даты» в списке «Все», не приписывается молча сегодняшнему дню. Для назначения времени затем выбирается дата. Это расширение прежней обязательной logicalDate, а не существующая возможность.
- «Фиксация после размещения» хранит предпочтение закрепления будущего блока; без блока занятых часов нет.

Пустой объём без полного интервала предлагается сохранять как отдельное состояние: durationPolicy=null, remainingWorkMinutes=null у незавершённого выполнения; после завершения остаток0, после снятия отметки снова null. Происхождение объёма (ручной/из интервала/не задан) хранится явно. Известный fixedWork N и его история сохраняются. Длина блока и отметка завершения не превращаются в фактически отработанное время.

Пустое начало не подставляет09:00. Неполное время сохраняется на сервере и в локальном восстановлении, а не только в несохранённом draft. Без полноценного интервала блок не создаётся. Новые nullable date/work и время намерения требуют согласованного изменения контрактов чтения/записи, валидации, БД и sync.

Для everyN предлагается постоянная дата привязки: выбранная дата или явно показанная дата создания в зоне правила. N — положительное целое число календарных дней. Генерация через N локальных календарных дней; нет UTC+24h, сдвига фазы после простоя или создания истории до правила. Дата окончания включительна. Прежние horizon31, bounded catch-up, уникальные slots, stop без удаления, opId/ownership/версии сохраняются.

### Одинаковые часы повторения

В предлагаемом U1 часы формы относятся ко всей новой серии. Полные интервалы автоматически размещают новые выполнения на соответствующие даты — это явное расширение прежнего R1, где worker создаёт только незапланированные выполнения. При конфликте, несовместимости ручного объёма, отсутствующем местном времени или неразрешённой неоднозначности DST выполнение сохраняется без блока с видимой причиной: ничего не сдвигается, чужое время не перезаписывается. Автоматически вычисленный объём определяется для каждого дневного интервала по elapsed minutes; ручной объём не меняется. Неполные часы сохраняются без размещения. Появление блока атомарно учитывается в scheduleVersion и журнале; согласованная синхронизация не публикует часть операции.

Weekly и everyN альтернативны: выбранные дни/пресеты образуют weekly, everyN не пересекается молча с weekday-фильтром. Без выбранного повторения создаётся одно выполнение. Конец серии не заменяет время конца каждого выполнения.

## Область изменения и сохранность

После выбора конкретного пакета оформить точный общий контракт, аддитивную миграцию и согласованное обновление Backend/Web/sync validation. Область разрешения U1: nullable logicalDate/durationPolicy/remainingWorkMinutes; сохраняемое время намерения и происхождение объёма; interval-вариант recurrence с intervalDays/anchorDate и общими часами серии; совместимые версии read/write/sync и безопасное автоматическое размещение. Architect фиксирует точные DTO и правила совместимости до интеграции. Не выдавать «каждые N дней» за weekly-набор, пустой объём за0/60, пустое начало за выбранное пользователем время. Не менять прежние snapshots условий, Completion/history, результаты операций, существующие calendar blocks и frozen pending. Прежние черновики должны открываться в единой форме с прежними ID и сохранёнными настройками.

Независимая работа сейчас ограничена перестановкой имеющихся полей и явной необязательностью описания. Это не полная реализация U1. Удаление вкладок должно сопровождаться единой формой с сохранением ввода при выборе повторения, а не скрытым переключением двух независимых черновиков.

Фактический результат независимой части: frontend изменил только DefinitionForm.tsx и ConstraintsForm.tsx, переставил существующие поля, добавил метку необязательного описания и optional children-slot для метаданных. Check/build PASS,42/42 существующих regression-теста PASS; отдельное CLI-ревью read-only/approval never — конкретных P0–P3 нет. Обязательность дат/объёма, прежние вкладки, DTO, guards и черновики на этом шаге не менялись. Не выдавать его за выполненную единую форму. Финальная проверка Markdown-ссылок/diff --check прошла.

## Критерии приёмки

- Поля идут в указанном порядке; только название обязательно, остальные оговорённые поля действительно могут отсутствовать по выбранной семантике.
- Сохранение и редактирование без скрытой подстановки времени/объёма; понятные ошибки несовместимых границ и фиксированного объёма.
- Weekly/everyN создают независимые выполнения; каждый интервал и конец повторения соблюдаются, DST и простой не сдвигают привязку.
- Завершение/отмена без известного объёма не теряют состояние; известный объём не меняется из-за формы.
- Две вкладки, повтор доставки, конфликты, старые черновики и потеря ACK сохраняют данные и исходную операцию.
- Backup/restore перед миграцией, подходящие PostgreSQL/Web проверки, браузер и read-only reviewer.
