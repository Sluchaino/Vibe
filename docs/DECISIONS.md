# Vibe — реестр решений и предложений ADR

Архитектура в целом: DRAFT. Узкие утверждённые решения перечислены отдельно; остальные предложения ADR остаются PROPOSED. Статусы: INPUT-CONSTRAINT (задано владельцем), PROPOSED, ACCEPTED, REJECTED, SUPERSEDED. ACCEPTED ставится только на основании явного выбора владельца с датой и указанием поручения.

## Предложения

| ID / статус | Предложение и причина | Рассмотренные альтернативы | Последствия / что утвердить |
| --- | --- | --- | --- |
| ADR-01 PROPOSED | Модульный монолит ASP.NET Core + PostgreSQL, логические Domain/Application/Infrastructure/API. Один пользовательский план требует согласованных транзакций | Микросервисы сейчас усложняют версии, deploy и транзакции; отдельный solver-service возможен позднее | Границы модулей и каталоги backend/android/web/contracts; число проектов определить при каркасе |
| ADR-02 PROPOSED | TaskDefinition, TaskOccurrence, CalendarBlock, Completion и WorkSession разделены | Одна таблица «task» смешивает повторения, части и факты | Одобрить логическую модель и историю/снимки; физическую схему проектировать отдельно |
| ADR-03 PROPOSED | Room как источник UI, атомарная outbox, повтор доставки и серверные версии | Network-first нарушает заданные офлайн-сценарии; синхронизация только по timestamp теряет конфликты | Одобрить локальный overlay/shadow, pending/conflict UX и worker стратегию |
| ADR-04 PROPOSED | Planning adapter к OR-Tools CP-SAT; Dijkstra для путей; конечный горизонт и timeout | Greedy list scheduling проще для ограниченного MVP, но имеет меньше возможностей; новый научный алгоритм не нужен | Выбрать solver после spike C#/native, дискретность/горизонт/бюджет и политику remainingWork |
| ADR-05 PROPOSED | REST/JSON + OpenAPI, единый контракт и compatibility checks до клиентов | Ручные разные DTO дрейфуют; GraphQL/BFF не обоснованы текущими сценариями | Согласовать ресурсы, id/enum/time/error/concurrency; выбрать генератор отдельно |
| ADR-06 PROPOSED | entityVersion + opId + change-log cursor + tombstones; атомарный confirm сравнивает planningInputRevision и scheduleVersion | Last-write-wins по часам устройства опасен; version только расписания пропускает изменения входов | Одобрить manual conflict MVP, snapshot-resync, сроки dedup/log и защиту stale proposal |
| ADR-07 PROPOSED | UTC instants + IANA timezone для правил; локальные недели; отдельный useful time; Completion по occurrence | UTC+24h неверно для локального дня/DST; считать goal по календарным частям неверно | Выбрать DST policy, начало недели, факт vs logicalDate, reopen, timer recovery и параллельные таймеры |
| ADR-08 PROPOSED | Полный объём сохраняется при split; отдых после последней части; task→rest→travel; preview перед принятием | Потеря хвоста/неявное сокращение недопустимы; совмещение отдыха с дорогой не задано | Одобрить отдых на часть/выполнение, резерв timer-breaks, неизвестные места и порядок мягких целей |
| ADR-09 PROPOSED | Ограниченный вертикальный MVP из ROADMAP, затем полный набор F01–F13 | Полный solver/все экраны первым этапом увеличивают риск до проверки sync | Выбрать MVP и включение базовых дороги/отдыха; отложенные функции не отменяются |

## Решения, которые ещё не подготовлены как ADR

Архитектурный smoke-review уточнил PROPOSED ADR-02/06/07: согласованный снимок входов и версий; уникальность Completion независимо от opId двух устройств; взаимоисключающие режимы длительности; стабильный слот повторения и сохранение досрочных завершений; timezone-снимок недельного периода. Эти уточнения внесены в документы как предложения, а не утверждения.

Identity/auth без платных внешних сервисов по умолчанию; версии .NET/EF/SDK/Android API/React и библиотек; лицензия календаря и solver packaging; политика хранения/удаления/backup; поддерживаемое время offline; измеримые performance-бюджеты; хостинг. До выбора нельзя подставлять произвольные значения как согласованные.

## Запись утверждения

Для каждого выбранного ADR координатор добавляет: дату; кто утвердил (владелец); точную формулировку и параметры; указание на сообщение/поручение; последствия/изменённые документы. Отклонённые альтернативы сейчас лишь рассмотрены командой, не отвергнуты владельцем. Изменение ACCEPTED оформляется новым решением и согласованием, не тихой правкой истории.
