# R1 — одноразовые и повторяющиеся задачи

Статус: ACCEPTED / 17.10.2026. Владелец выбрал «Утвердить R1 и реализовать; дробление позже» в ответ на этот пакет; запись R1 в DECISIONS.md. Разрешены оформление точного контракта и реализация Backend/Web в описанных границах. Независимые пункты 2–5 WEB-UX-03 реализуются отдельно.

## Что увидит пользователь

При создании по умолчанию открыта вкладка «Одноразовая», рядом — «Повторяющаяся». Одноразовая означает одну цель с одним фактом завершения; работа несколько дней не превращает её в повторяющуюся. В R1 у одноразовой сохраняются нынешние параметры и цельный блок. Дробление фиксированного объёма на части требует следующего отдельного серверного среза; неработающей галки не будет.

Повторяющаяся имеет название, условия и объём одного выполнения, дни недели, дату начала и необязательную дату окончания. Наборы «Каждый день», «Будни», «Выходные» выбирают соответствующие дни. У каждого дня своё выполнение и отметка завершения. Сервер создаёт их на 31 день вперёд и продлевает горизонт без открытого браузера; это не ограничение срока жизни задачи одним месяцем.

Выполнения создаются без занятого времени в календаре. Время размещается отдельно прежними действиями. Массовое назначение одинакового времени серии, каждые N дней, месячные повторения, исключения, редактирование/возобновление правила и дробление в R1 не входят.

Кнопка «Остановить повторение» прекращает создание новых выполнений. Уже созданные, в том числе будущие, сохраняются. Остановка не удаляет данные и не отменяет отметки.

## Модель и API для согласования

Одно RecurrenceRule на definition: id, definitionId, pattern=weekly, daysOfWeek, timezone, startDate, endDate|null, enabled, generatedThrough|null, serverVersion. Наличие правила определяет повторяющуюся задачу, в том числе после остановки. Старые определения и их ручные выполнения сохраняются; по числу выполнений тип не угадывается. RecurrenceSlot связывает userId/ruleId/slotDate с occurrenceId; уникальность слота не зависит от версии правила.

Предлагаются:

- POST /api/v1/task-definitions/{id}/recurrence-rule: opId, id, definitionVersion, pattern=weekly, daysOfWeek, timezone, startDate, endDate → rule и planState (201).
- GET /api/v1/recurrence-rules/{id} → rule и planState, ETag serverVersion.
- POST /api/v1/recurrence-rules/{id}/stop: opId и rule If-Match → остановленное правило и planState.

Identity/antiforgery/ownership, явные конфликты и прежний replay сохраняются. Записи rule/slot/occurrence/версий/dedup/log атомарны под пользовательским guard. Worker генерирует порциями не более 31 локального дня, без истории до создания правила; пропуски после простоя догоняются. Timezone правила фиксируется независимо от дальнейшего изменения пользовательской зоны. Генерация не создаёт календарных блоков, не меняет scheduleVersion и сохраняет отдельные snapshots/Completion каждого выполнения.

S1 потребует согласованного расширения Backend/Web: новый sync kind recurrence, соответствующая версия формата, несколько последовательных single-item log rows одной команды с уникальностью opId+ordinal. Оболочка batch не вводится. Для согласованной публикации клиент накапливает bounded delta-проход до hasMore=false; старые результаты операций сохраняются. Точный OpenAPI и проверки совместимости оформляет координатор после выбора пакета, до интеграции клиентов.

## Проверки и пределы

Проверяются replay/crash/две вкладки, повтор worker без дублей, гонка stop/worker, чужие ссылки, независимые complete/reopen, sync pageSize=1, DST/смена зоны, границы недели/месяца/года и сохранность прежних данных. При достижении существующего ограничения sync snapshot нужна явная ошибка; автоматическая очистка истории не входит. Новые таблицы и индексы только аддитивные, перед миграцией резервная копия и проверка восстановления.
