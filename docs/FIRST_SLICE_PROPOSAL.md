# Vibe — выбор технического каркаса и первого Web-среза

Статус: T0 ACCEPTED 10.10.2026, D1-01–05 ACCEPTED 12.10.2026. C08 задаёт Web первым демо; C09 разрешает начать разработку Backend/Web. Утверждения и точные границы записаны координатором в [DECISIONS.md](DECISIONS.md). Архитектура вне этих пакетов остаётся DRAFT. Android, офлайн-задачи и таймер остаются в полном плане; их инструменты сейчас не устанавливаются.

## T0 — короткий выбор, позволяющий начать каркас

**Утверждённый выбор T0:** создать `backend/` с одним запускаемым ASP.NET Core Web API на .NET 10 и `web/` с React/TypeScript/Vite; реализовать только локальный health endpoint и оболочку Web, проверить сборку и запуск. Предметный API, хранение задач и auth начинаются после отдельного выбора D1. Это узкое техническое решение, не утверждение всего ADR-01 или ADR-05.

| Что входит | Что проверить |
| --- | --- |
| Один серверный проект `backend/Vibe.Api`; логические предметные модули добавляются после согласования | Проект собирается; локальный `GET /health` возвращает 200 и только состояние процесса, без секретов/диагностики машины |
| React/TypeScript/Vite в `web/`; стартовая страница Vibe и получение health через локальный proxy | TypeScript-проверка и production build проходят; страница открывается и различает доступный/недоступный Backend |
| Локальные инструкции запуска, настройки без секретов, lock-файл Web у одного владельца | Запуск воспроизводится по инструкции; сетевое прослушивание ограничено локальной машиной; фиктивные задачи и фиктивный вход не выдаются за работу приложения |

.NET 10 утверждён как target T0; global.json фиксирует установленный SDK 10.0.400 с latestPatch. Установленные SDK/runtime, Node/pnpm и отсутствие проверенной БД описаны координатором в [DEV_ENVIRONMENT.md](DEV_ENVIRONMENT.md). Точные версии Web-пакетов зафиксированы в package.json и lock-файле после чтения registry и проверки сборки; это не утверждение будущих EF Core/Android/solver-зависимостей.

T0 не требует Docker, PostgreSQL или Android SDK: health проверяет процесс, а не подключение к БД. PostgreSQL/EF Core сохраняются заданным стеком для хранения; готовность сохраняющего среза нельзя доказывать памятью или SQLite. Сейчас Docker engine выключен, реальное подключение PostgreSQL не проверено. Публикация, глобальные настройки, коммит и push не входят в T0.

Альтернатива: сначала полностью выбрать D1 и подготовить PostgreSQL, затем создавать каркас. Это уменьшает число промежуточных состояний, но откладывает проверку сборки/запуска без необходимости. Другой frontend build tool или другой поддерживаемый .NET target возможны по выбору владельца; оснований менять заданные языки и платформы нет.

## D1 — утверждённый пакет для сохраняющего Web-демо

Владелец выбрал пять решений D1-01–D1-05 вместе 12.10.2026. В таблице ниже сохранены причины и рассмотренные альтернативы; выбраны рекомендуемые варианты. До интеграции предметных клиентов оформляется OpenAPI-контракт с примерами по этому пакету; новые изменения общего контракта требуют отдельного выбора владельца.

| ID / статус | Рекомендуемый выбор | Причина и альтернатива |
| --- | --- | --- |
| D1-01 ACCEPTED | Ручные задачи/выполнения, список незапланированных, календарь день/неделя; фиксированный неделимый объём, одно явно заданное пользователем место, без обязательного отдыха | Проверяет сохранение и календарь без зависимости от solver/Android. Альтернатива — включить граф и отдых раньше, с расширением модели/валидации и приёмки |
| D1-02 ACCEPTED | Разделить definition/occurrence/block/fact; отдельные importance/difficulty/executionPriority; occurrence хранит снимок своих ограничений | Сохраняет целевую модель F01–F13. Альтернатива с одной сущностью task смешивает план и факт, поэтому не рекомендуется |
| D1-03 ACCEPTED | UTC интервалы, IANA зона пользователя, локальные окна, точность до минуты; ручной ввод не сдвигает DST-время молча | Проверяемый календарь без скрытой потери времени. Автоматическая политика DST для будущих повторений выбирается позже |
| D1-04 ACCEPTED | REST/JSON `/api/v1`, серверные версии/ETag, явные конфликты, атомарные ручные календарные команды и отдельные revision | Закладывает совместимость Android и защиту будущего preview. Last-write-wins по часам устройства не рекомендуется |
| D1-05 ACCEPTED | ASP.NET Core Identity, Web-сеанс через same-origin cookie и antiforgery; две изолированные локальные учётные записи, без публичной регистрации | Реальная проверка владельца данных без платного identity-сервиса. Альтернатива — согласованный внешний/self-hosted OIDC, который требует отдельной настройки |

D1 не включает Completion UI, таймер, статистику, автоматическое планирование, flexible/split, повторения, цели, шаблоны и месяц. Они остаются в R4–R8 [ROADMAP.md](ROADMAP.md). D1 закрывает только выбранную часть F01/F08 и сохраняет возможность остальных требований; он не объявляется полным MVP.

## Минимальная модель D1

| Сущность | Предлагаемые данные и поведение |
| --- | --- |
| UserSettings | Владелец из identity, IANA timezone, начало недели Monday; один пользовательский контекст Place для D1 |
| Category / Place | UUID, владелец, имя, serverVersion. Place задаёт пользователь, без координат; D1 допускает только одно место пользователя |
| TaskDefinition | UUID, title, description, categoryId?, importance, difficulty, executionPriority, durationPolicy, mobilityPolicy, availabilityRules, placeId, requiredRestMinutes, serverVersion |
| TaskOccurrence | UUID, definitionId, manual logicalDate, снимок duration/mobility/availability/place/rest и исходной definitionVersion, serverVersion. Один definition может иметь несколько ручных occurrence за одну дату |
| CalendarBlock | UUID, occurrenceId, kind=task, startInstant/endInstant, fixed, serverVersion; D1 допускает ноль или один блок на occurrence |
| Completion | Отдельный будущий факт: максимум один действующий на occurrence. В D1 не создаётся; календарный блок не означает завершение |
| UserPlanState | planningInputRevision и scheduleVersion для атомарной защиты пользовательского плана |

Предлагаемые шкалы: `importance=low|normal|high`; `difficulty=light|medium|heavy`; `executionPriority` — целое 1–5, больше означает более высокий пользовательский приоритет. Эти значения сохраняются независимо; D1 не вычисляет одно из другого. Названия/границы шкал входят в D1-02, а не уже заданы владельцем.

Для D1 `durationPolicy={mode:fixedWork, requiredWorkMinutes:N}`, N — положительное целое; `splitAllowed=false`, `requiredRestMinutes=0`. Flexible использует отдельную будущую ветвь модели, а не min/desired/max как разрешение сократить fixedWork. Пока нет фактов выполнения, remainingWorkMinutes=N. Длина единственного блока равна N минутам реального прошедшего времени; иначе запись отклоняется, весь объём остаётся незапланированным. Округление и потеря хвоста запрещены.

Редактирование definition влияет на новые occurrence. Уже созданный снимок не меняется молча; его изменение — отдельная версионируемая команда. Если новые ограничения occurrence нарушают существующее размещение, команда отклоняется до явного снятия/изменения блока; скрытого изменения календаря нет. D1 не содержит удаления definition и каскадов: этот сценарий проектируется вместе с tombstones/историей на R4.

Предлагаемая семантика mobility: `movable|fixedAfterPlacement`. Второй режим закрепляет выбранное время после первого размещения; пользовательский `CalendarBlock.fixed` также защищает блок. Это запрет автоматического/случайного переноса. Осознанная ручная правка закреплённого блока требует отдельного подтверждения в UI и явного признака намерения в календарной команде. Альтернатива — абсолютный запрет любой правки до снятия фиксации; её можно выбрать вместо этой семантики.

## Время и серверная валидация

Интервалы полуоткрытые `[start,end)`, на чтении — ISO 8601 UTC с `Z`; точность размещения — целая минута без сетки 5/15 минут. Локальная дата occurrence не заменяет instant. День/неделя строятся по IANA зоне и локальным границам, не через прибавление 24 часов к UTC. Смена зоны меняет отображение абсолютных блоков, а не их положение во времени.

Ручная команда размещения содержит localStart, timezone и явно выбранный UTC offset. Сервер проверяет их согласованность и разрешает UTC instant; endInstant выводится из фиксированного объёма. Для несуществующего localStart возвращается ошибка. При неоднозначном времени UI предлагает оба offset, а сервер принимает только действительный выбранный. Это политика ручного ввода D1; предложение сдвигать время автоматических повторений в PLANNING_RULES не утверждается этим выбором.

AvailabilityRules — выбранные дни недели и локальные интервалы в снимке timezone; отсутствие окон явно означает любые дни/время. Интервал через полночь нормализуется, блок должен целиком помещаться в разрешённом окне. Если граница окна попадает в DST-gap/overlap, сервер требует явного уточнения исключения для этой даты и не разрешает размещение через неопределённую границу. Невозможное размещение возвращает причину, а occurrence остаётся видимым незапланированным.

Сервер независимо от Web проверяет непустой title, корректность enum/целых минут, допустимые окна, полную длительность, отсутствие пересечений, версии и принадлежность всех ссылок. Предлагаемые защитные границы DTO: title 1–200 символов, description до 4000, имена категории/места 1–100; списки — до 100 объектов на страницу, календарный запрос — до 31 локального дня. Это параметры предложения, не измеренные performance-бюджеты.

Все размещаемые D1-задачи указывают единственный явный Place пользователя. Ненулевой отдых, flexible, split, правило повторения, цель или другой/неизвестный place не отбрасываются и не превращаются в допустимые значения: неподдерживаемая команда отклоняется с `unsupportedConstraint`. Неизвестные изменяемые поля также не игнорируются. При чтении позднее появившейся расширенной задачи D1-клиент не перезаписывает её сокращённым DTO. Направленный граф, отсутствие пути, обязательный отдых и timer-breaks остаются отдельными будущими правилами, а не нулевыми значениями по умолчанию для неизвестных данных.

## Предлагаемая поверхность API и версии

Это список для подготовки контракта после выбора, не существующие endpoints. В изменяемых DTO нет доверенного клиентского owner/userId; UUID допускает генерацию клиентом. Enum передаются строками, версии — непрозрачными строками, чтобы JavaScript не терял точность больших чисел.

| Ресурс/команда | Назначение |
| --- | --- |
| `GET /api/v1/me`; `GET/PUT /api/v1/settings` | Текущий пользователь и настройки зоны/недели/единственного места |
| `GET/POST /api/v1/categories` | Список и создание пользовательских категорий |
| `GET/POST /api/v1/task-definitions`; `GET/PUT /api/v1/task-definitions/{id}` | Пагинированный список, создание и полная правка definition |
| `POST /api/v1/task-definitions/{id}/occurrences`; `GET /api/v1/occurrences`; `GET/PUT /api/v1/occurrences/{id}` | Создать occurrence из явно проверенной definitionVersion, читать и явно менять его снимок |
| `GET /api/v1/calendar?from=...&to=...` | Блоки в полуоткрытом диапазоне instant и обе актуальные revision |
| `POST /api/v1/occurrences/{id}/placement` | Атомарное `place\|move\|unplace\|setFixed`, с baseScheduleVersion и текущей версией occurrence |

`serverVersion` каждой сущности представлен ETag. Правка требует `If-Match`; отсутствие условия даёт 428, устаревшая версия — 412. Создание occurrence сверяет переданную definitionVersion; календарная команда дополнительно сверяет baseScheduleVersion и возвращает 409 `staleSchedule` при несовпадении. Изменение блока также повышает версию occurrence, чтобы все его календарные команды конкурировали на одной базе.

Ручная календарная команда в одной транзакции проверяет версии/ограничения/пересечения, записывает block/occurrence и увеличивает scheduleVersion и planningInputRevision. Все влияющие на план изменения definition/occurrence/settings также атомарно увеличивают planningInputRevision. Общий guard строки UserPlanState сериализует такие записи одного пользователя; проверка revision вне транзакции недостаточна.

Мутации несут opId UUID. В D1 результат и отпечаток семантического запроса хранятся атомарно с изменением, в области аутентифицированного пользователя. Повтор идентичного opId возвращает прежний результат, изменённый запрос — 409 `idempotencyMismatch`. Автоматической очистки этой истории в локальном D1 нет; retention и безопасный resync выбираются на R4 до длительной офлайн-доставки. Поздний ответ повтора не должен затереть более свежую редакцию Web. Это минимальная идемпотентность D1, не реализованный полный sync/change-log.

Ошибки — ProblemDetails с устойчивым code, fieldErrors при валидации и correlationId; 400 для неверных/неподдерживаемых данных, 401 без сеанса, 403 для запрета/невалидного antiforgery, 404 для отсутствующей или чужой сущности. Ответы конфликтов содержат только данные текущего владельца. API/schema version, serverVersion, opId, будущий syncCursor, planningInputRevision и scheduleVersion имеют разные назначения; timestamp устройства не выбирает победителя.

До R6 дополнительно утвердить согласованный PostgreSQL snapshot и preview/confirm: proposal связывает обе revision, confirm сравнивает их под тем же guard и атомарно пишет план; расчёт не удерживает длинную транзакцию. Ручной путь D1 не должен стать обходом будущего stale-guard. В D1 preview/solver не реализуются.

## Auth для первого сохраняющего среза

Рекомендуется ASP.NET Core Identity с хранением пользователей в PostgreSQL; браузерный сеанс через HttpOnly/Secure cookie с SameSite=Strict. Web и API имеют один origin, локальная разработка использует proxy. HTTPS и явная antiforgery-проверка обязательны для изменяющих cookie-auth запросов, включая login/logout; SameSite не заменяет antiforgery. Выбор cookie для браузерного приложения опирается на [документацию Identity для SPA](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization), необходимость CSRF-защиты — на [документацию ASP.NET Core antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery). Это предложение конфигурации, а не утверждение, что auth уже реализована.

Для локального D1 предлагаются два заранее подготовленных тестовых аккаунта; `GET /api/v1/auth/antiforgery` для bootstrap, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` и `GET /api/v1/me`; ограничение попыток входа. Учётные данные поступают через локальные секреты; публичная регистрация, email-доставка, recovery и внешние identity-сервисы не входят в D1. Сохраняющие endpoints защищены по умолчанию. При истечении сеанса API возвращает 401, Web сохраняет несохранённый ввод в пределах текущего аккаунта и предлагает вход; при смене аккаунта не отправляет старые данные под новой identity.

Нужно проверять владельца каждой сущности и каждой ссылки, а не только фильтровать списки. ETag, UUID, deviceId и opId не являются правом доступа. Кэш Web привязан к identity и очищается/переключается при logout. Логи не содержат пароли, cookie, токены и тексты личных задач. Auth нельзя заменять заголовком с произвольным userId или фиктивным входом даже для демонстрации разделения данных.

Параметры TTL сеанса, lockout и хранения ключей фиксируются в конфигурации и проверках D1 до открытия сохраняющего среза; срок поддержки offline, mobile token flow и смена аккаунта с Room pending выбираются отдельно до R4–R5. Выбор Web cookie не определяет будущую Android-аутентификацию и не меняет общий предметный API.

## Готовность и следующие решения

T0 завершён, когда сборки и локальный health/UI действительно проверены, инструкции воспроизводимы и reviewer рассмотрел результат. Это частичная техническая подготовка R2, не готовность D1/auth/БД.

D1 завершён после проверенного пути «войти → создать definition → создать occurrence → вручную разместить → перезагрузить → увидеть сохранённое». Обязательны проверки: две вкладки с одной версией; два аккаунта и чужие id/ссылки; неверный/отсутствующий antiforgery; повтор после commit и изменённый payload opId; fixedWork 90 минут против окна 60; пересечения/граница суток/DST; закреплённый блок; неподдерживаемые ограничения без обнуления. Reviewer проверяет результат, существенные замечания исправляются. В T0/D1 нет требования установить Android SDK.

До сохраняющего D1 нужны явный выбор пакета, формальный API-контракт и проверенный PostgreSQL. До Android — ADR-03 и полный ADR-06, retention/resync и recovery таймера. До solver — ADR-04/08 и расширение ADR-07 по остатку, DST повторений, отдыху, дороге, целям/неделям и стабильности. До выпуска — хостинг, backup/restore, удаления, поддерживаемые платформы и измеримые бюджеты. Новые научные алгоритмы не разрабатываются.
