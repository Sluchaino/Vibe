# Vibe — проект синхронизации

Статус: DRAFT / PROPOSED ADR-03/06. Это спецификация поведения для обсуждения, не реализованный протокол.

## Источники состояния и версии

На Android UI читает Room. Сервер принимает авторитетные изменения после проверки инвариантов и версий; клиент хранит подтверждённую базу + локальный pending overlay. Web работает через тот же предметный API и concurrency-правила.

| Значение | Назначение |
| --- | --- |
| API/schema version | Совместимость формата контракта и локальной схемы |
| entity serverVersion | Конкурентное изменение конкретной сущности |
| deviceId + opId | Идемпотентность и диагностика доставки; не право доступа |
| per-entity local sequence | Порядок зависимых локальных операций |
| syncCursor | Позиция в серверном change log, непрозрачная клиенту |
| planningInputRevision | Любое серверное изменение входов, влияющих на расчёт |
| scheduleVersion | Версия принятого расписания, включая ручные правки |

Часы устройства и modifiedAt не выбирают победителя конфликта. Все операции проверяют аутентифицированного пользователя; чужой id/cursor/opId не даёт доступа.

## Локальная запись и outbox

1. В одной Room-транзакции изменить локальную сущность и записать операцию с UUID, baseVersion, порядком и зависимостями. UI показывает pending.
2. Операция сохраняется до подтверждённого результата. Очередь переживает process death и отсутствие сети. Не подтверждать запись только наличием временного объекта в памяти.
3. Worker при сети отправляет готовые операции; create идёт до ссылающихся update/session/completion. Зависимые операции одной сущности не отправляются конкурентно. Независимые можно batch по согласованному пределу.
4. После принятия первой правки обновить baseVersion следующей из известного результата, сохранив её смысл. Не отправлять вторую правку с заведомо старой базой и не «исправлять» baseVersion слепо поверх чужой правки.
5. Повторы с backoff/jitter и ручное «синхронизировать сейчас». Retry для сети/временных ошибок; validation/auth/conflict — отдельные состояния, без бесконечного автоматического повторения.

Произвольная compaction очереди небезопасна: нельзя потерять семантику Completion, удаления или событий таймера. Возможная compaction нескольких правок одного поля требует отдельного доказанного правила.

## Push, идемпотентность и атомарность

PROPOSED: сервер принимает opId, entityId, operationType, baseVersion, payload и зависимости. В транзакции проверяет пользователя, наличие предыдущего результата opId, concurrency-токен и инварианты; пишет сущность, результат операции и запись change log атомарно.

Повтор той же операции возвращает прежний результат. Тот же opId с другим payload отклоняется. Тайм-аут после серверного commit разрешается повторной доставкой, а не созданием второго факта. Срок хранения dedup-результатов должен покрывать поддерживаемый offline/retry период; при истечении — явный протокол resync, не обещание вечной идемпотентности.

Batch возвращает результат каждой операции. Ошибку одной независимой операции не выдавать за успех всего batch. Для согласованного изменения серии/расписания/каскада удаления использовать атомарный предметный сценарий, не набор несвязанных CRUD-записей.

## Pull и локальные pending-правки

Сервер отдаёт страницу изменений и nextCursor из стабильной последовательности. Cursor, содержимое страницы и tombstones применяются в одной Room-транзакции; при сбое повтор страницы безопасен.

Если локальная сущность clean — применить свежую подтверждённую версию. Если есть pending — обновить server shadow, сохранить overlay и обнаружить конфликт; не затереть локальную правку pull-ответом. ACK старой операции также не должен перезаписать более новую локальную правку.

При устаревшем cursor сервер явно требует snapshot-resync. Клиент сначала сохраняет pending операции/обе конфликтующие редакции, затем транзакционно обновляет подтверждённый снимок и cursor. Согласовать consistent snapshot watermark, срок change log и tombstones, максимальное время offline. Полная очистка Room вместе с pending недопустима.

## Конфликты

Несовпадение baseVersion возвращает conflict с актуальной версией и данными, необходимыми для решения, без записи поверх сервера.

PROPOSED первоначальная политика: ручной выбор «оставить серверную / применить мою поверх свежей базы / объединить поля» с повторной проверкой. Автоматическое слияние непересекающихся текстовых полей возможно позднее. Время, длительность, статус, повторения и расписание не сливать механическим last-write-wins.

Удаление против редактирования — явный конфликт; старое update не воскрешает tombstone. Новое создание после удаления требует нового id или отдельной согласованной restore-команды. Независимые WorkInterval с уникальными id можно принимать без потери, но наложения/дубли и завершения разных устройств требуют проверки.

PROPOSED Completion — одна действующая запись на occurrence; повторная кнопка «готово» не увеличивает цель дважды. Reopen/correction имеет версию и историю, пересчитывает статистику и planningInputRevision. OPEN: параллельные таймеры одного occurrence, активный таймер при удалении задачи, корректировки ручного времени.

Уточнение PROPOSED: уникальность действующего Completion обеспечивается БД по occurrence и предметной транзакцией, независимо от opId. Два устройства могут отправить разные opId/Completion id: эквивалентное повторное завершение возвращает канонический факт без дополнительного очка; несовместимое время/содержание даёт конфликт для решения. Reopen меняет версионируемое состояние и аудит; устаревшее завершение после reopen не принимается как новое без согласованной базы. Независимые полезные интервалы при этом не теряются.

## Защита от устаревшего расписания

Каждый proposal включает basePlanningInputRevision, baseScheduleVersion и id снимка/горизонт. При подтверждении сервер в одной транзакции сравнивает текущие значения и версии самого proposal, повторно проверяет существенные ограничения и увеличивает scheduleVersion. Конкурентное подтверждение/правка может пройти только одно; второе получает stale/conflict. Повтор идентичного confirm-opId возвращает прежний результат.

Снимок и обе revision берутся из одного согласованного состояния БД. Запись входа с изменением revision атомарна; confirm и все изменяющие план транзакции должны разделять общий per-user concurrency guard. Иначе чтение revision перед записью оставляет окно гонки. Конкретный механизм блокировки/условной записи утвердить и проверить конкурентным интеграционным тестом.

PlanningInputRevision меняется при задачах, occurrence, completion/остатке, графе, доступности, целях/повторениях и влияющих настройках, даже если accepted schedule ещё не изменился. Ручная правка календаря меняет scheduleVersion и при необходимости planningInputRevision. Все пути записи должны следовать этому правилу.

Android не подтверждает серверный proposal автоматически, пока есть локальные изменения его входов: сначала отправить pending, разрешить конфликты, получить актуальную базу, пересчитать/обновить preview. Offline preview помечается cached; новое серверное планирование требует сети. При pull применять только более новую принятую версию, не потеряв локальные намерения; сравнение версий не заменяет показ конфликта.

## Таймер и фактическое время

Состояние таймера и интервалы сохраняются локально с уникальными id. Активное время измеряется monotonic clock; pause и break не считаются useful work. При process death восстанавливается сохранённое состояние; после reboot или изменения wall-clock нельзя молча записывать отрицательный/огромный интервал — нужна выбранная recovery-политика и, при неопределённости, подтверждение пользователя.

Синхронизация событий не запускает таймер на другом устройстве и не создаёт второй WorkInterval при retry. Полезное время статистики считается из принятых интервалов с обработкой коррекций; cached Android-статистика показывает pending/неполноту.

## Будущая приёмка

Проверить потерю сети до/после commit, дубли/изменённый payload opId, ACK после новой локальной правки, два устройства и одну baseVersion, delete/update, порядок create/update, partial batch, cursor expiry/snapshot, page replay, crash в Room-транзакции, Completion/reopen и stale confirm при новом факте. Реализация и тесты сейчас отсутствуют.
