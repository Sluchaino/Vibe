# Vibe — продукт и требования

Статус: DRAFT. Источник REQ — исходный запрос владельца от 10.10.2026. Архитектурные, численные и продуктовые уточнения ниже не утверждены.

## Назначение и платформы

Vibe — персональный планировщик задач, который строит реалистичное расписание, помогает выполнять работу и показывает фактический прогресс. REQ: Backend — C#, ASP.NET Core Web API, PostgreSQL, EF Core; Android — Kotlin, Jetpack Compose, Room, offline-first; Web — React и TypeScript с общим серверным API.

REQ: первоначальный автоматический планировщик работает на сервере, возможный локальный Android-планировщик — будущее расширение. Использовать существующие алгоритмы, без разработки нового научного алгоритма. Места и направленное время дороги задаёт пользователь, без GPS, карт и геолокации.

## Пользовательские сценарии

1. Пользователь создаёт задачу «Подготовить отчёт», задаёт место, допустимые вечера, объём и возможность частей. Получает предложенный план с дорогой/отдыхом и подтверждает его.
2. В метро без интернета пользователь меняет описание задачи, создаёт новую и запускает таймер. Изменения сохраняются локально, затем отправляются один раз по смыслу, даже при повторных попытках доставки.
3. На Web пользователь параллельно меняет ту же задачу. Android обнаруживает конфликт версий и позволяет выбрать разрешение, сохраняя обе редакции до выбора.
4. Пропущено одно занятие для недельной цели. Перепланирование предлагает оставшиеся выполнения на свободное время текущей недели, сохраняя фиксированные блоки.
5. Пользователь завершает выполнение из нескольких частей. Цель увеличивается на одно выполнение; фактическая работа берётся из таймера/подтверждённой ручной записи, а не из длины всех резервов.
6. Расписание изменилось на другом устройстве после открытия preview. Подтверждение старого предложения отклоняется и предлагает обновить план.

## Нефункциональные требования

REQ: устойчивые офлайн-функции Android, синхронизация между устройствами и сохранение существующего поведения при изменениях.

PROPOSED: отсутствие молчаливой потери правок; атомарность локальной записи задачи с очередью; идемпотентные серверные операции; явная версия схемы; изоляция данных пользователей; защищённый транспорт; отсутствие секретов в репозитории и логах; доступные формы и календарь; наблюдаемость ошибок синхронизации/планирования без содержания личных задач в логах.

PROPOSED: хранить абсолютные события времени как UTC instant, правила повторения как локальное время + IANA timezone; учитывать DST и смену часового пояса. Конкретная политика неоднозначного/несуществующего времени требует выбора.

OPEN: поддерживаемые Android API/браузеры и версии SDK, срок поддержки, размер данных и горизонта, p95 API/планирования, timeout solver, бюджет памяти/батареи, политика резервных копий, удаления и хранения истории. Не выдавать предполагаемые значения за измеренные SLA.

## Границы первого выпуска и открытые вопросы

Полный набор F01–F13 — целевой продукт. Предлагаемый первый MVP покрывает меньший вертикальный срез, описанный в ROADMAP.md; сокращение MVP требует согласия и не отменяет остальных требований.

OPEN: означает ли «запрет переноса» фиксацию уже выбранного времени или фиксированный интервал при создании; единицы/шкалы важности и сложности; какой приоритет пользовательский, а какой рассчитанный; правило завершения фиксированного объёма; одно или несколько мест у задачи; отдых после каждой части или после последней; начало недели; сочетание повторения с недельной целью; правила пропусков и переносов повторений; таймер одновременно на устройствах; аутентификация и экспорт/удаление данных.

Шаблон, повторение, недельная цель и таймер не являются взаимозаменяемыми механизмами. Автопланирование не обещает вместить невозможную совокупность ограничений: невместившиеся задачи должны оставаться видимыми с причиной.
