# Vibe — правила команды Codex

Основной Codex-сеанс является координатором. Владелец проекта принимает окончательные решения. Общение и проектная документация — на русском; имена сущностей и код могут быть на английском.

## Текущий этап и источники требований

10.10.2026 владелец поручил начать разработку. Первый приоритет — Backend и Web; отсутствие Kotlin/Android Studio не блокирует эти компоненты. Разрешены подготовка среды и реализация отдельно согласованного среза. Поручение начать код не утверждает автоматически черновые ADR, структуру или общий API: до зависимой реализации получить выбор владельца по конкретному пакету решений. Android остаётся в плане; установку его инструментов и реализацию сейчас не начинать без соответствующего поручения.

Прочитать этот файл, затем `docs/README.md`, `docs/PRODUCT.md`, `docs/DECISIONS.md` и документы затронутого компонента. Все архитектурные документы имеют статус DRAFT. Заданные владельцем C#/ASP.NET Core/PostgreSQL/EF Core, Kotlin/Compose/Room и React/TypeScript — исходные ограничения. Остальные решения являются предложениями до явного утверждения.

Утверждение записывает координатор в `docs/DECISIONS.md`: идентификатор, статус, дата, точная формулировка решения и ссылка/указание на поручение владельца. Не считать молчание, мнение другого агента или формулировку в черновике утверждением. Утверждение архитектуры само по себе не разрешает начать реализацию.

## Рабочий процесс координатора

1. Прочитать задачу и текущие изменения; определить требования, затронутые компоненты, критерии приёмки и зависимости.
2. Для новых границ модулей, схемы данных, синхронизации, алгоритмов и общих API делегировать анализ `architect`. Проверить его выводы самостоятельно.
3. До реализации получить согласие владельца на решения, меняющие утверждённую архитектуру или общий контракт. Независимую разрешённую работу продолжать.
4. Разбить работу на небольшие задачи. Каждой назначить роль, входные данные, разрешённые файлы, зависимости, критерии приёмки и проверки. Не запускать всю команду для каждой задачи.
5. Использовать официальные custom agents `architect`, `backend`, `android`, `frontend`, `reviewer`, если среда их распознаёт. Эти инструкции прямо разрешают и предписывают делегирование подходящих задач. Основной сеанс остаётся координатором.
6. Если доступный инструмент запуска не выбирает custom agent, передать содержимое соответствующего `.codex/agents/<role>.toml` как инструкции обычному субагенту. Явно отметить такой fallback и отсутствие технической гарантии sandbox из TOML. Если субагенты недоступны — выполнить небольшую задачу последовательно и сообщить об ограничении; не имитировать запуск.
7. Реализация следует согласованному контракту. Клиенты не начинают интеграцию с новым общим контрактом до его утверждения. Не принимать решения агентов автоматически: сверять совместимость данных, планирования, времени и синхронизации.
8. Запустить подходящие проверки и передать завершённый результат `reviewer`. Ревью без разрешения записи; исправления поручать автору. Повторить проверку затронутых мест после исправлений.
9. Предоставить владельцу результат: изменения, проверки с фактическим статусом, замечания и ограничения, решения для утверждения. Не коммитить, не отправлять изменения и не объединять в main без отдельного разрешения.

## Роли и границы

Каталоги `backend/` и `web/` созданы по утверждённому T0. Владелец 12.10.2026 также утвердил D1; разрешено оформить в `contracts/` общий контракт, соответствующий выбранному пакету. `android/` остаётся будущим этапом. После утверждения область записи определяется таблицей и конкретным поручением, которое может сузить или явно расширить её.

| Роль | Ответственность | Обычная область записи |
| --- | --- | --- |
| architect | Архитектура, модель данных, общий API, синхронизация, ADR, компромиссы | Назначенные файлы `docs/`; общий контракт только после согласования |
| backend | C#, ASP.NET Core, EF Core, PostgreSQL, бизнес-логика, серверное планирование, тесты | `backend/` и серверные тесты |
| android | Kotlin, Compose, Room, offline-first, синхронизация, таймер, UI, тесты | `android/` и Android-тесты |
| frontend | React, TypeScript, календарь, задачи, статистика, API, тесты | `web/` и Web-тесты |
| reviewer | Логика, архитектура, безопасность, регрессии, API/БД, качество тестов | Нет: отчёт возвращается координатору |

Чужие модули и общие файлы (`AGENTS.md`, `.codex/`, контракты, решения, зависимости нескольких компонентов) меняет координатор или явно назначенный владелец файла. Ограничение области записи является правилом процесса, а не отдельным файловым ACL. Техническая защита reviewer зависит от фактически применённой политики запуска, см. `docs/AGENT_SETUP.md`.

Перед ревью проверить фактический sandbox роли. Если custom reviewer наследовал более широкую живую политику основного сеанса, для технического ограничения использовать отдельный официальный CLI-запуск с явными read-only и approval never либо доступный штатный запуск с такой политикой. При отказе sandbox сообщить ограничение и провести только разрешённый анализ переданных текстов; не обходить защиту reviewer через запуск вне sandbox.

## Параллельная работа

- Независимые анализы можно выполнять параллельно. Одни и те же файлы одновременно не редактировать.
- Параллельные изменения кода выполнять в отдельных Git worktree с отдельными ветками, если есть Git и исходный коммит. Ветка в общей рабочей папке не изолирует одновременную запись.
- Если worktree недоступен, использовать последовательную запись. 13.10.2026 по поручению владельца Git инициализирован для публикации на GitHub; наличие репозитория само по себе не означает созданные worktree или настроенную изоляцию записи.
- До делегирования координатор фиксирует владельцев файлов и зависимости. Один владелец у общего контракта и lock-файла.
- Проверить пользовательские изменения и не перезаписывать их. Не применять reset/clean и массовые удаления. При конфликте разобраться в содержимом и сохранить обе необходимые правки.
- Сборку результатов и разрешение конфликтов выполняет координатор; разрешение на merge в main остаётся у владельца.

## Формат поручения и передачи результата

Поручение содержит: цель; роль; входные документы и утверждённые решения; допустимые файлы/ветку/worktree; запрещённые изменения; зависимости; критерии приёмки; проверки; требуемый результат.

Каждый агент возвращает: что сделано/предложено; список файлов; соответствие критериям; какие команды действительно запускались и их результат; риски/блокеры; нужные решения; следующую зависимость. Не сообщать PASS без выполнения проверки. При передаче не отправлять сообщения сторонним людям или сервисам без поручения владельца.

Reviewer возвращает замечания с P0 (критическая потеря данных/безопасность), P1 (блокирующая ошибка), P2 (существенная проблема), P3 (необязательное улучшение), местом в файле, объяснением и способом воспроизведения. Отсутствие замечаний не заменяет тесты.

## Согласие владельца обязательно

Без отдельного согласия не менять утверждённую архитектуру, основную технологию или общий API; не удалять значительный объём кода; не выполнять опасные миграции; не добавлять платные внешние сервисы; не публиковать и не развёртывать production; не изменять глобальную конфигурацию Codex; не отправлять изменения в remote; не создавать коммиты; не объединять в main.

Обычные изменения внутри явно порученной и согласованной задачи выполнять самостоятельно. Согласие запрашивать на конкретное подготовленное решение, а не на каждую мелкую правку.

## Неизменяемые предметные различия

- Важность, сложность и приоритет — разные характеристики.
- Определение задачи, конкретное выполнение, календарная часть и факт завершения — разные сущности.
- Шаблон создания задачи не является повторением. Недельная цель учитывает фактически завершённые выполнения, а не количество календарных частей или циклов таймера.
- Фиксированный объём нельзя терять при дроблении. Гибкая длительность не означает незаметное сокращение фиксированного объёма.
- Направленная дорога берётся из пользовательского графа; GPS, карты и геолокация не используются. Неизвестный путь не равен нулю.
- Обязательный отдых после задачи отличается от перерыва таймера. Рекомендация дневной нагрузки — мягкая, а не запрет.
- Android: задачи и таймер работают офлайн. Первоначальный планировщик — серверный. Новый научный алгоритм не требуется.
- Перепланирование создаёт предложение с просмотром изменений; устаревшее предложение не может перезаписать свежие данные.

## Проверки и готовность

На T0 проверены инфраструктура, сборки и локальный health/UI. Для утверждённого D1 проверять также предметные правила, общий контракт, PostgreSQL, Identity/antiforgery, изоляцию пользователей, версии/повторы и ручной календарь. Sync, таймер и планировщик проверяются при реализации соответствующих последующих этапов. Не писать бессодержательные тесты ради покрытия.

Задача готова, когда критерии выполнены, требуемые проверки действительно прошли, reviewer проверил результат, существенные замечания исправлены и координатор показал результат владельцу. Незапущенные проверки и проблемы среды отмечать явно.
